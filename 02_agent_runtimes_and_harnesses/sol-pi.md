## 🎯 1. В чем идея и философия проекта?

При длительной работе автономных кодинг-агентов накапливается колоссальный объем паразитных накладных расходов:
1. **Повторяющиеся ходы (Repeated Turns):** Каждая правка файла почти всегда сопровождается отдельным ходом для вызова команды сборки или тестов (`edit` $ightarrow$ ответ модели $ightarrow$ `bash` $ightarrow$ ответ модели).
2. **Бесполезный реплей контекста:** Огромные текстовые наблюдения (листинги директорий, grep-поиски, логи) пересылаются на каждом последующем шаге диалога, пожирая кэш и лимиты токенов.
3. **Чтение «мусорных» логов:** Дорогие флагманские модели (Claude Opus, GPT-4o) тратят целый запрос на чтение 500-строчного лога компилятора, хотя для решения задачи критичны всего 3–4 строки с ошибкой.

Команда **Nvidia Research** подошла к этому с позиции исследователей автоматических циклов (Auto-Research Loops):
> *«Прежде чем бездумно масштабировать агентные циклы вычислений, могут ли агенты сделать сам исполнительный харнес радикально более экономичным и быстрым?»*

**SoL-Pi** — это модульное автономное расширение для терминального агента **Pi**, объединяющее четыре проверенных механизма эффективности. Проект следует принципу: **сокращать затраты токенов и ходов, не останавливая работу раньше времени, не пропуская валидацию и не скрывая доказательств (evidence).**

## 🧱 2. Четыре фундаментальных механизма SoL-Pi

```text
┌────────────────────────────────────────────────────────────────────────┐
│                     SOL-PI EFFICIENCY ARCHITECTURE                     │
├──────────────────────────┬─────────────────────────────────────────────┤
│ 1. ACTION FUSION         │ Инструменты: слияние правки файла и запуска │
│    (Слияние действий)    │ тестов в единый атомарный вызов tool-call   │
├──────────────────────────┼─────────────────────────────────────────────┤
│ 2. OBSERVATION PACK      │ Наблюдения: замена больших выводов тулов на │
│    (Хэндлы наблюдений)   │ стабильные хэндлы с постраничным отзывом    │
├──────────────────────────┼─────────────────────────────────────────────┤
│ 3. EVIDENCE REDUCER      │ Делегирование: верифицируемое сжатие логов  │
│    (Сжатие логов)        │ дешевой моделью со строгой проверкой цитат  │
├──────────────────────────┼─────────────────────────────────────────────┤
│ 4. ONLINE CONTEXT        │ Контекст: эвристическая компактификация     │
│    COMPACT (Компакт)     │ только на границах шагов с оценкой выгоды   │
└──────────────────────────┴─────────────────────────────────────────────┘
```

### 1. Action Fusion (Слияние мутации и проверки)
* **Проблема:** В стандартных циклах агент тратит 2 полноценных обращения к LLM: сначала вызывает инструмент `edit`/`write`, ждет подтверждения, затем в новом ходе вызывает `bash: npm test`.
* **Решение SoL-Pi:** Расширяет инструменты `edit` и `write` опциональным объектом `then_run`.
* **Как работает:** Агент передает текст правки и сразу команду валидации. Харнес атомарно применяет изменение к файлу, тут же исполняет команду проверки и возвращает **одно объединенное наблюдение**. Решение модели между двумя ходами исчезает, экономя время и задержку сети.

### 2. ObservationPack (Стабильные хэндлы вместо полотен текста)
* **Проблема:** Если агент сделал широкий поиск по коду или вывел большой файл, этот текст остается в истории и повторно пересылается на каждом последующем ходе.
* **Решение SoL-Pi:** Тяжелые текстовые результаты архивируются в локальное хранилище сессии (`<session>/sol-pi/observation-pack/`), а в активный контекст проецируется компактный дескриптор (хэндл).
* **Постраничный вызов:** При необходимости агент может в любой момент запросить точный фрагмент через инструмент `obs_recall`.

### 3. Evidence-Preserving Reducer (Верифицируемое сжатие логов)
* **Проблема:** Логи сборки или падения тестов занимают тысячи токенов. Передавать их целиком дорого, а просить основную модель сжать их — значит тратить те же дорогие токены.
* **Решение SoL-Pi:** Перенаправляет длинные диагностические логи на специализированную легкую и дешевую модель-редуктор (через `evidencePreservingReducerModel`).
* **Гарантия точности (Evidence Preservation):** Сжатый квиток (receipt) принимается харнесом **только тогда, когда каждая сохраненная цитата посимвольно совпадает с заархивированным оригиналом**. Если модель-редуктор сгаллюцинировала или исказила стек-трейс, сжатие отклоняется, и в контекст безопасно попадает оригинальный лог.

### 4. Online Context Compact (Экономическая компактификация)
* **Проблема:** «Слепая» авто-компактификация посреди сложного рассуждения сбивает мыслительный процесс агента.
* **Решение SoL-Pi:** Запускает компактификацию только на естественных контрольных точках — при обновлении плана (`update_plan`), когда подзадача успешно завершена.
* **Формула выгоды (`cacheWriteReadRatio`):** Харнес оценивает соотношение стоимости записи кэша к чтению (по умолчанию `12.5`). Компактификация выполняется только если выгода от освобождения контекста превышает стоимость перезаписи кэша. После успешного сжатия агент плавно продолжает работу в новом ходу.

## 🛡️ 3. Четыре железных правила проектирования

Nvidia сформулировала строгие ограничения, чтобы оптимизации не ломали надежность:
1. **Никаких патчей ядра Pi (No Pi patches):** SoL-Pi использует только официальные публичные Extension API Pi, не заменяя исходный код рантайма.
2. **Явный Opt-In (Explicit opt-in):** По умолчанию все 4 механизма отключены. Активация происходит осознанно через конфигурационный файл.
3. **Сохранение доказательств (Preserve evidence):** Исходные логи и наблюдения всегда сохраняются на локальном диске сессии (`<session-id>/sol-pi/`). Никакие данные не теряются безвозвратно.
4. **Контроль хост-рантайма:** Аутентификация, токены провайдеров, выбор базовой модели и шелл остаются под строгим контролем основного окружения.

## ⚙️ 4. Конфигурация (`sol-pi.json`)

Файл конфигурации ищется в следующем порядке:
1. `.pi/sol-pi.json` (в доверенном локальном проекте)
2. `~/.pi/agent/sol-pi.json` (глобально для пользователя)

### Пример: Консервативный профиль (100% локально, без внешних вызовов)
Включает только слияние действий и локальные хэндлы наблюдений:
```json
{
  "version": 1,
  "actionFusion": true,
  "observationPack": true,
  "evidencePreservingReducer": false,
  "onlineContextCompact": false,
  "cacheWriteReadRatio": 12.5
}
```

### Пример: Максимальный профиль (All-Enabled)
Включает все 4 механизма с отдельной моделью для сжатия логов:
```json
{
  "version": 1,
  "actionFusion": true,
  "observationPack": true,
  "evidencePreservingReducer": true,
  "evidencePreservingReducerProvider": "openrouter",
  "evidencePreservingReducerModel": "qwen/qwen-2.5-coder-32b-instruct",
  "onlineContextCompact": true,
  "cacheWriteReadRatio": 12.5
}
```

## 🚀 5. Установка и запуск

```bash
# 1. Установка базового рантайма Pi (Node.js 22.19+)
npm install --global @earendil-works/pi-coding-agent@0.84.2

# 2. Установка расширения SoL-Pi напрямую из репозитория Nvidia
pi install git:github.com/NVlabs/SoL-Pi

# Или локально только для текущего репозитория:
pi install git:github.com/NVlabs/SoL-Pi --local --approve

# 3. Валидация конфигурации перед запуском
node scripts/check-sol-pi-config.mjs --config ~/.pi/agent/sol-pi.json
```

## 💡 Практические выводы для других агентов (Claude Code, Cursor, Antigravity)

Архитектура SoL-Pi дает готовые паттерны проектирования для любого агентного харнеса:
* **Паттерн `Mutation + Validation` в одном инструменте:** Вместо двух тулов `edit_file` и `run_tests` объединение их в `edit_and_test` экономит до 30–40% лишних сетевых ходов агента.
* **Strict Verification для сжатия:** Никогда не доверять слепо суммаризации логов сторонней LLM без посимвольной проверки цитат по архиву.
* **Экономика контекста:** Компактифицировать контекст не по фиксированному таймеру, а в точках смены состояний плана с учетом кэширования промптов (Prompt Caching).
