# 🔀 Архитектура Tool Broker & Execution Blocker: Проектирование шлюзов вызова и защиты инструментов AI-агентов

> **Архитектурное руководство по проектированию промежуточного брокера и защитного блокера (Tool Broker & Blocker Gateway) между языковыми моделями и исполняемыми инструментами (MCP, REST, CLI).**  
> **Обобщает опыт проектов:** IBM ContextForge, Archestra, Composio, ACI.dev, Pipelock и инварианты `ai_pentester`.

---

## 🎯 1. Почему прямой вызов тулов (Direct Tool Calling) признан антипаттерном?

В ранних агентных системах архитектура строилась наивно: в системный промпт модели передавался массив со всеми доступными функциями. На практике в продакшене это привело к четырем фатальным проблемам:

1. **Раздутие контекста (Context Bloat) и деградация рассуждений:**  
   Описания 100 инструментов на базе JSON Schema занимают от 30 000 до 60 000 токенов. Модель тратит вычислительный ресурс на разбор бесполезных схем, начинает галлюцинировать параметрами и ошибаться в логике.
2. **«Смертельная триада» (Lethal Trifecta):**  
   Классическая уязвимость безопасности: если агент одновременно имеет *доступ к конфиденциальным данным* (например, чтение файлов), *обрабатывает недоверенный ввод извне* (веб-страницы, тикеты) и *имеет сетевой инструмент* (`curl`, `send_email`), любая атака Indirect Prompt Injection гарантированно приводит к сливу данных.
3. **Утечка учетных данных:**  
   Если передать токен GitHub или Stripe внутрь контекста LLM, он неизбежно всплывет в логах, системных ответах или в теле внешнего запроса.
4. **Зацикливание (Runaway Tool Loops) и финансовые риски:**  
   При ошибках валидации модель может бесконечно повторять один и тот же вызов (например, создание 500 тикетов в Jira или повторная отправка 1000 писем), исчерпывая лимиты бюджета.

**Решение:** Выделенный слой **Tool Broker & Execution Blocker** — автономный прокси-сервер, выступающий как диспетчер, маршрутизатор и жесткий полиси-блокер.

## ⚙️ 3. Пять ключевых компонентов современного брокера

### 1. Semantic Tool Router (Tool-RAG & Dynamic Pruning)
* **Проблема:** В каталоге компании доступно 800 MCP-инструментов.
* **Как работает брокер:**  
  1. Каталог всех инструментов индексируется локальной векторной моделью (или BM25).
  2. Модели дается только один мета-инструмент: `search_tools(query: string)`.
  3. Либо брокер на каждом шаге автономно анализирует последний шаг рассуждения агента, выполняет векторный поиск по каталогу схем и **динамически подмешивает в следующий промпт только 3–5 релевантных инструментов**.
  4. Как только задача выполнена, нерелевантные схемы выгружаются из контекста.

### 2. Lethal-Trifecta Interceptor (Блокер смертельной триады)
* **Проблема:** Эксфильтрация данных через сговор уязвимостей.
* **Как работает блокер:**  
  Брокер ведет **граф состояния контекста сессии (Taint Tracking)**:
  * Если в текущей сессии сработал инструмент с меткой `data_source: private` (чтение локального файла, запрос к внутренней БД), сессия помечается флагом `TAINTED_PRIVATE`.
  * Если после этого агент пытается вызвать инструмент с меткой `network_egress: external` (`send_http`, `webhook`, `dns_lookup`), брокер **физически блокирует запрос** или принудительно перенаправляет его на экран подтверждения человека (HITL).

### 3. Loop-Breaker & Idempotency Engine (Защита от зацикливания)
* **Как работает блокер:**  
  * На каждый вызов вычисляется хэш параметров: `H = SHA256(ToolName + Args)`.
  * Брокер ведет скользящее окно последних $N$ вызовов.
  * Если фиксируется повтор одинакового действия с одинаковой ошибкой более 2 раз — брокер прерывает цепочку с типизированной ошибкой: `ActionLoopDetectedError: Вызов повторяется без прогресса. Измените стратегию`.
  * Автоматическая генерация `Idempotency-Key` для финансовых и транзакционных API.

### 4. Credential Offloading (Секреты за пределами памяти агента)
* **Как работает брокер:**  
  * Агент передает только бизнес-параметры: `{"user_id": "42"}`.
  * Брокер сопоставляет идентификатор сессии с защищенным хранилищем секретов (Vault / Keyring / Encrypted Store).
  * На уровне исходящего сетевого сокета брокер добавляет заголовки `Authorization: Bearer <real_token>`, `X-Api-Key: ...`.
  * Реальный ключ никогда не попадает в оперативную память LLM и не может быть выведен наружу через атаки промпт-инъекций.

### 5. Response Compactor & Truncation Filter (Защита контекста от взрыва)
* **Проблема:** Инструмент (например, `kubectl get pods` или SQL-запрос) возвращает JSON на 8 мегабайт. При попадании в контекст такой ответ парализует модель.
* **Как работает брокер:**  
  * Потоковая фильтрация: брокер оставляет только ключи первого уровня или применяет JSONPath-фильтр, запрошенный агентом.
  * При превышении лимита (например, 2048 токенов) брокер автоматически сохраняет полный ответ во временный локальный файл на диске, а агенту отдает структурированную выжимку:  
    `{"preview": [...первые 5 записей...], "total_count": 1400, "spill_file": "/tmp/artifacts/res_42.json"}`.

## 📋 5. Чек-лист проектирования собственного Tool Broker & Blocker

При проектировании локального или корпоративного брокера тулов проверьте реализацию ключевых слоев:

### 🔹 1. Диспетчеризация и контекст (Broker Layer)
- [ ] Реализован семантический поиск по инструментам (*Tool-RAG*): в контекст никогда не подается больше 5–7 схем одновременно.
- [ ] Описания инструментов сжаты (удален избыточный вербозный текст, используется компактная JSON Schema).
- [ ] Поддерживается федерация протоколов: единый шлюз умеет транслировать вызовы в MCP stdio, MCP SSE и REST.

### 🔹 2. Безопасность и политики (Blocker Layer)
- [ ] **Lethal Trifecta Guard:** запрещен одновременный неконтролируемый доступ к чтению приватных данных и внешней сети.
- [ ] **Credential Offloading:** сырые токены и API-ключи хранятся в защищенном хранилище и подставляются брокером на уровне сокета.
- [ ] **Loop-Breaker:** реализован подсчет одинаковых вызовов с принудительной остановкой зациклившегося агента.
- [ ] **Human-in-the-Loop:** опасные деструктивные действия требуют интерактивного подтверждения с криптографическим дайджестом.

### 🔹 3. Обработка результатов (Sanitization Layer)
- [ ] Внедрен жесткий лимит на размер возвращаемого телом инструмента текста (per-call payload cap).
- [ ] Крупные дампы автоматически сбрасываются в локальные файлы-артефакты с передачей агенту краткой выжимки.
- [ ] Ответы тулов фильтруются на предмет случайного присутствия паролей, токенов и PII.
